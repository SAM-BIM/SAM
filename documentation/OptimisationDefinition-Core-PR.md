# SAM.Core.Optimisation: the declarative Optimisation Definition (Q4) - SAM

Branch `feature/optimisation-definition-core` -> base `sow/2026-Q4` (cut from `b081065e`). Record date: 2026-10-08.

This is PR3 of the SAM Native Optimisation declarative/engineering-UX phase. In that plan:
- PR1 (SAM_UI) is wording and layout;
- PR2 (SAM#186) adds units and display formatting;
- PR3 (this PR) is the definition core.

PR1–PR3 are independent. **PR4+ (SAM_Tas adapter, SAM_UI form ⇄ definition ⇄ AI) wait for owner review of these foundations.** Nothing consumes this library yet. No existing project changes behaviour, and **SAM.Math is untouched.**

## Current status

PR open, **not merged**. New netstandard2.0 library `SAM.Core.Optimisation` (references SAM.Units only), its tests, and fixtures. `SAM.sln` and `SAM.Tests.csproj` gain the project; nothing else changes.

## Why

The native optimiser (Java-free GenOpt PR1–PR6) is configured only through a SAM_UI form, which:
- is session-only;
- can't be saved, shared, read by Grasshopper or an agent, or safely generated by AI.

This PR adds one strongly typed, engine-neutral **Optimisation Definition** that:
- humans, SAM_UI, Grasshopper and AI can all read and write;
- is a plain declarative document: no C#, no Tas code, no expressions;
- has strict reading and layered validation with engineering messages.

The engine (SAM_Tas for `tas-script`, PR4) supplies its **capabilities** and runs a definition. The core never executes anything.

## Ownership (architecture decision D1)

The library lives in SAM as a new project, `SAM.Core.Optimisation` (precedent: `SAM.Core.Reporting`), and not inside SAM.Math. The reasons:
- the accepted kernel binary stays frozen;
- SAM.Math would otherwise need SAM.Units;
- SAM.Math ships to many host folders, where stale copies were the PR5 deployment problem.

Dependency direction: SAM_UI → SAM_Tas → SAM.Core.Optimisation → SAM.Units. Nothing points back to a UI.

## The schema `sam.optimisation/1` (JSON)

JSON was chosen over YAML and SAM's `_type` JSON (plan §5):
- AI generation is reliable with it, and structured-output APIs support it;
- System.Text.Json already exists in SAM;
- it has no implicit-typing traps;
- round-tripping is deterministic;
- the identifier is a stable name, not an assembly-qualified type.

A proven example, `SAM/SAM.Tests/Golden/Optimisation/systems-demo-golden-section.json`, is byte-for-byte the canonical writer output:

```json
{
  "schema": "sam.optimisation/1",
  "name": "Systems Demo – heat pump controller setpoint (golden section)",
  "description": "Find the HeatPumpController setpoint that gives the lowest annual cost.",
  "model": {
    "engine": "tas-script",
    "description": "Systems Training model (TBD, TSD, TPD). The script sets the plant-room HeatPumpController setpoint, simulates the plant for the year and reports annual results."
  },
  "variables": [
    {
      "name": "Setpoint",
      "description": "Setpoint of the HeatPumpController in plant room 1",
      "type": "continuous",
      "minimum": -5,
      "maximum": 35,
      "start": 3,
      "step": 1
    }
  ],
  "outputs": [
    { "name": "Result", "description": "Annual cost; the script's objective value (equal to Cost)", "quantity": "currency", "unit": "GBP" },
    { "name": "Cost", "description": "Annual cost", "quantity": "currency", "unit": "GBP" },
    { "name": "CO2", "description": "Annual CO2" }
  ],
  "objective": { "output": "Result", "sense": "minimise" },
  "method": { "algorithm": "golden-section", "tolerance": 0.1 },
  "stopping": { "maximumSimulations": 2000 }
}
```

(The outputs, objective and method are shown compacted here; the canonical file puts every property on its own line.)

**Fixture values:**
- The fixture equals the PR5 Systems Demo example: Setpoint −5…35, start 3 / step 1. The method settings are the SAM_Tas defaults: AbsDiffFunction 0.1, MaxIte 2000.
- The Hooke–Jeeves fixture has start 10 / step 2, stepReductionFactor 2, initialStepExponent 0, stepExponentIncrement 1, stepReductions 4. These are the SAM_Tas `GPSHookeJeevesAlgorithm` defaults, verified.

**Units and descriptions come only from the actual PR5 Systems Demo `Script.txt` (SHA-256 `d68a7e2e…`), checked 2026-10-08:**
- **Setpoint has no unit.** The script writes `Variables["Setpoint"]` into the TPD `HeatPumpController.Setpoint`, whose unit depends on the controller's sensor in the `.tpd`; the script does not state it.
- **Result and Cost are GBP.** The script comments "Annual Cost (GBP)" and sets `dTotal = dCost`, so Result equals Cost by construction.
- **CO2 has no unit** (the script states none).

**Schema contents:**

| Object | Fields | Notes |
|---|---|---|
| definition | schema (required), name, description, notes, model (required), variables (required), outputs (required), objective (required), constraints, method (required), stopping | — |
| model | engine (required), description | No path: local files are an engine setting, never in the portable definition |
| variable | name, minimum, maximum (required); description, type (`continuous`; `integer`/`discrete` reserved), quantity, unit, start, step | — |
| output | name (required), description, quantity, unit, aggregation | Aggregation is informational: the script computes the value |
| objective | output, sense (`minimise` / `maximise`), both required | **No implicit minimise** |
| constraints[] | output, exactly one of `atMost` / `atLeast`, unit | In the schema; runnable only where the engine enforces constraints |
| method | `golden-section`: tolerance · `hooke-jeeves`: stepReductionFactor, initialStepExponent, stepExponentIncrement, stepReductions | A null setting means the engine default |
| stopping | maximumSimulations | — |

**Other schema properties:**
- Quantities: `dimensionless`, `temperature`, `temperature-difference`, `percent`, `time`, `power`, `energy`, `mass`, `carbon`, `currency`, `angle`, `length`, `area`.
- Units: `-`, `%`, `°C`, `°F`, `K` (temperature difference), `h`, `W`, `kW`, `Wh`, `kWh`, `MWh`, `kg`, `t`, `kgCO2e`, `tCO2e`, `GBP`, `EUR`, `USD`, `°`, `m`, `m²`, plus synonyms such as `degC` → `°C`.
- Units are **declarations**: SAM never verifies them against the model.
- `Query.SchemaText()` returns the JSON Schema (2020-12), an embedded resource. A test keeps it identical to the reader's field and enum tables.

## Work completed (all in `SAM/SAM.Core.Optimisation`)

**Model:**
- `OptimisationDefinition`, `OptimisationModel`, `DesignVariable`, `OptimisationOutput` (`RecordedOutputs()`), `OptimisationObjective`, `OptimisationConstraint`, `OptimisationMethod` / `GoldenSectionMethod` / `HookeJeevesMethod`, `StoppingCriteria`.
- Enums: `ObjectiveSense`, `OptimisationAlgorithm`, `DesignVariableType`, `OptimisationQuantity`, `DiagnosticSeverity`.
- SAM style: mutable, with deep copy constructors.
- **A semantically invalid definition is representable**, so either the form or the text view can show and fix it.

**Reading: `Create.OptimisationDefinition(text, out diagnostics, capabilities = null, extract = false)`.**
- **Strict.** A hand-written binder over a position-aware `Utf8JsonReader` tree gives every finding its line and column.
- **Returns null on any OPT1xx error.** Otherwise it returns the definition plus OPT2xx–4xx findings, located in the text.
- **Lenient where safe:**
  - comments and trailing commas (warning OPT114: comments are not kept);
  - BOM;
  - enum values differing only in case or separators (info OPT113, normalised);
  - unit synonyms (info OPT301, normalised).
- **`extract: true` (pasting an AI reply)** takes the first balanced, valid JSON object and drops a Markdown fence or prose with warning OPT115. Fenced text without `extract` is a syntax error.
- **Numbers keep their exact text** and are parsed by the runtime's correctly rounded parser.

**Writing: `Convert.ToJson()`.**
- Canonical: fixed property order, 2-space indent, `\n` line ends.
- Shortest round-trip invariant numbers, **bit-exact on read-back**.
- Non-ASCII written as is (`°C`).
- Optional unset values and an empty constraint list are omitted; a non-finite number is omitted, so reading reports it missing.

**Validation: `Query.Diagnostics(definition, capabilities = null)`, `Query.IsRunnable(...)`.**
- Stable codes, engineering wording, path, optional line/column, hint.
- **Capability findings make a definition non-runnable, never unreadable.** An imported definition with maximise or a constraint is kept, shown and editable, but cannot run on an engine that lacks the feature.

**Capabilities:** `IOptimisationCapabilities` / `OptimisationCapabilities` / `OptimisationAlgorithmCapability`. Each engine describes what it runs; the core ships no Tas instance (PR4 adds it).

**Catalogue:** `OptimisationCatalogue` / `OptimisationCatalogueEntry` hold the names a model makes available. For Tas, PR4 fills it from a script scan.

**AI exchange text: `Query.AIExchangeText(definition, capabilities, catalogue, task)`.**
- The strict contract: **exactly one raw JSON object, no Markdown or code fence, no prose; first character "{", last "}"**.
- Schema rules **generated from the capabilities**, so it offers only what the engine runs. On a minimise-only engine without constraints, "maximise", "constraint" and "atMost" never appear.
- The available names, the current definition as raw canonical JSON (no fence), and the task.
- A "cannot be expressed → return unchanged and explain in notes" escape.
- **No path or machine detail:** the builder takes none, and the definition holds none.

## Decisions and assumptions
- **Strict reading** blocks unknown fields and numbers-as-text. **Validation results are layered**: unknown units are only a warning (units are descriptive), while unsupported capabilities make a definition non-runnable but still loadable.
- **`sense` is required** in the text: no implicit minimise.
- **`K` means temperature difference** (engineering convention). **Carbon and mass units are interchangeable** for a carbon or mass quantity.
- **Method settings and `maximumSimulations` are optional.** Null means "engine default"; the engine (PR4) resolves it.
- **Golden section start/step are kept and written when present.** SAM_Tas passes them into `Variables.txt`, so PR4 can keep the evaluation inputs byte-identical to PR5 (plan risk R2).
- **No `IJSAMObject` embedding yet.** That comes in V1.1 with the Grasshopper components.
- **No unit conversion in V1** (constraints are not runnable on Tas), so there is no compile-time dependency on SAM#186. Units map to `SAM.Units.UnitType` by name at run time; `kWh`/`kg` resolve once SAM#186 is in the same build.
- **`.samopt.json` save/open is deferred to V1.1** (owner decision). The text is exchanged by copy/paste in V1.

## Unresolved issues and risks
- **Library not deployed.** It needs to ship beside SAM_UI and in the Grasshopper package once a consumer exists (plan PR8, SAM_Deploy, new assembly only).
- **Line/column for errors inside a pasted reply refer to the extracted object**, not the whole paste (stated in OPT115).
- **The column of a JSON syntax error counts bytes** (the System.Text.Json position). It can differ from characters on a line with non-ASCII text before the error. Positions of all other findings count characters.
- **Message quoting convention:** JSON field names appear in straight quotes ("maximum"), and user-chosen names in typographic quotes (“Setpoint”).
